# RAG 检索不准：先查证据，再改 Prompt

> 公开教学案例 · 2026-10-19 · JR Academy 教学资料。虚构公司、人工教学向量、离线结果；不调用模型，不是生产 RAG 或模型评测。

**先看完整成果：[逐题检索结果、答案与引用](RESULTS.md)。** 输入文档与七个英文测试问题在 [dataset.json](dataset.json)，计算过程在 [run.py](run.py)。不需要运行或配置账号就能读到结果。

## 一个看起来相关、实际会误导的答案

AtlasDesk 客服收到 v2 的 E1042 导出错误。人工教学向量的相似度排序把 D1 排在首位：把导出超时调到 120 秒。但 D1 属于已归档的 v1；v2 的正确证据是 D2：把超过 5000 行的导出拆成每批最多 5000 行，延长超时没有解决当前版本限制。

同一个错误码还出现在另一个虚构产品 HarborCRM 中，它需要重新连接存储目标。还有一份 v3 草案谈自动分页，尚未发布。关键词相同、语义相近，都不代表可以拿来回答当前产品的问题。

这个案例教读者交付一份**带文档引用的故障答复与检索诊断记录**。学习者需要基础 Python；无需向量数据库、API key 或 GPU。它没有实现真实问答产品。

这些文档正文全部随数据交付。产品与版本来自题目中已给定的上下文；代码没有实现自然语言实体识别。实际系统若拿不到版本，应先澄清，不能猜一个版本套规则。

## 四步实验，哪些是真算法，哪些是教学替代

1. **Dense 排序**：对人工写定的四维向量计算余弦相似度。向量只是演示“相近”为什么会误召回，不是某个 embedding 模型的输出。
2. **Lexical 排序**：英文分词后计算交集数量。为了让代码可以直接检查，未实现 BM25，也没有把它标成 BM25。
3. **RRF 融合**：按两路名次相加 `1 / (60 + rank)`，随后取前三个候选。这里 60 是融合常数，候选数是 3，两者不同。算法背景见 [Microsoft RRF 文档](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking)。
4. **证据筛选**：在候选中匹配产品、版本、current 状态和明确错误码，再取第一条；没有合适证据就返回 `INSUFFICIENT_EVIDENCE`。这是人工元数据规则，**不是神经重排器或 cross-encoder**。返回内容直接摘录文档，不是 LLM 生成。

示意路径：问题与已知上下文 → 两路排序 → RRF 前三名 → 元数据／错误码筛选 → 文档摘录或拒答。

## 已运行的结果，怎样读才不夸大

五个有答案问题中，人工向量 top 1 命中 4 个；RRF 前三名包含五个正确文档；候选规则最终选中五个正确文档。另两题分别问不存在的 v9 和没有证据的 E9999，单列检查拒答，不混入有答案问题的分母。

Q1 的 RRF 第一名仍然是 D1，正确文档 D2 在第二位。因此不能把本次成功全部归因于 RRF：如果过早只留第一名，后面的筛选也找不回 D2。规则成功还依赖结构化版本字段正确、索引内容及时、候选中有正确证据。

这些是特意构造的小数据结果，不代表真实检索准确率提升，也不能证明混合检索总是更好。下一阶段可以在获准的真实检索环境中比较 BM25、真实 embedding 与 reranker；本案例没有执行这些步骤。

## 本地复现

在本目录运行，Python 3.9+，仅标准库，无安装步骤：

```sh
python3 run.py
```

脚本重算本目录的 `result.json` 与 `RESULTS.md`，会替换这两个派生文件；不会读取凭据、访问网络或改网站。原始数据不会被修改。

建议先改 D2 的版本或状态，重跑后检查 Q1 是否失去证据；再恢复原值。实验使用的 gold_document 只用于计分，不参与候选选择。可阅读代码确认这一点。

## 带走的排查顺序

先确认正确文档是否存在，再查切分与召回；正确文档进了候选后，再查融合、过滤与重排；最后才检查回答是否忠实使用证据。分别记录召回与回答质量，避免用“最终答对了”掩盖检索问题。

若产品、版本或权限过滤是硬边界，应在检索层尽早执行，并在输出前复核；本案例后置筛选用于观察候选损失，不是推荐的多租户隔离实现。
